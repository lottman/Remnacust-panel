# База данных и перенос между версиями

## Версии PostgreSQL и обновление

Compose-файлы этого репозитория используют PostgreSQL **18.7**: [обычный](../panel/backend/docker-compose-prod.yml) и [раздельный](../panel/backend/docker-compose-advanced-prod.yml) варианты. Это настройка новой установки из этих файлов, а не версия любой работающей базы.

Обновление панели сохраняет существующий образ PostgreSQL и его том. Проверяйте фактическую версию через закрытое административное подключение командой SHOW server_version; и сверяйте её с выбранной процедурой обновления. Версия панели и версия БД независимы.

Результаты конкретных матриц и область проверки перечислены в [совместимости](COMPATIBILITY.md). Исторический успешный прогон не подтверждает применение новых миграций к вашей базе.

Для новой установки выбирайте поддерживаемую основную версию с текущими исправлениями. Плановый срок поддержки PostgreSQL 14 завершился **12 ноября 2026 года**. PostgreSQL 13 и более старые версии не входят в проверенный диапазон проекта. [Политика PostgreSQL](https://www.postgresql.org/support/versioning/).

В пределах одной основной версии обновляйте исправления после резервного копирования по инструкции выбранного выпуска PostgreSQL. Смена основной версии требует отдельного pg_upgrade или dump/restore. Нельзя подключать прежний data volume к образу другой основной версии. Сначала проверьте перенос на копии базы.

Утилита pg_dump не должна быть старше сервера-источника. Обратный перенос на более старую основную версию не гарантируется. Сохраните .env, APP_SECRET, резервную копию и совместимый прежний образ приложения.

## Сетевой диск и IOPS

Сетевой блочный диск допустим при достаточных IOPS, приемлемой задержке и надёжной фиксации записей. Нехватка производительности особенно заметна после запуска и при массовом обновлении подписок. Сравнивайте время ответа подписки, нагрузку диска, CPU и память. Не очищайте рабочие данные и не увеличивайте число подключений вслепую.

PostgreSQL требует надёжного сохранения подтверждённых записей. Для NFS отдельно проверьте режим монтирования и гарантии сервера; блочный том и NFS имеют разные требования. Не отключайте fsync ради скорости. [Требования PostgreSQL 18 к файловой системе](https://www.postgresql.org/docs/18/creating-cluster.html).

Диагностика БД может требовать отдельного административного доступа; она не заменяет журнал ошибок и проверку диска. Главная страница панели не показывает отдельный блок диагностики базы.

## Обновление панели

Сохраните резервную копию и окружение, затем обновите панель штатным способом. Миграции применяются при запуске. На большой базе предусмотрите окно обслуживания: изменения индексов могут временно задержать запись.

При ошибке прочитайте журнал и устраните причину до повтора. Не удаляйте историю миграций и не выполняйте сброс базы для обхода ошибки. Ошибка расшифровки старых секретов требует проверки исходного APP_SECRET, а не создания нового ключа.

## Исправление прежней базы для Remnawave

Старые установки Remnacust могут требовать восстановления стандартных имён таблиц администратора и настроек, а также формата пользовательских ключей. Исправление сохраняет пользователей, идентификаторы и связи. Исходный APP_SECRET обязателен.

Для такой установки сохранён scripts/restore-remnawave-database.sh. Это отдельная процедура совместимости, а не обычное обновление. Нужны существующая база, фактический Compose и заранее собранный совместимый образ. Всегда задавайте --image явно: историческое значение по умолчанию не обозначает текущий выпуск.

Предварительная проверка из корня исходников:

```bash
bash scripts/restore-remnawave-database.sh \
  --compose /opt/remnacust/panel/docker-compose.yml \
  --image remnacust-panel:local
```

Для применения после проверки добавьте --apply. Скрипт запросит подтверждение; неинтерактивный запуск требует --yes. Если окружение хранится отдельно, задайте --env-file; при необходимости задайте фактическое имя проекта через --project-name.

Скрипт сохраняет копию базы, Compose и окружения, останавливает процессы панели и исправляет старые данные. Если в ту же базу пишут другие приложения из отдельных установок, остановите их до применения. Неверный ключ или конфликт данных не должны разрешаться удалением таблиц наугад.

После успеха прежняя панель остаётся остановленной. Запускайте только совместимый новый образ. При обрыве связи результат может быть неизвестен: проверьте сохранённую копию и итоговое состояние до повторного запуска прежнего приложения.

## Переход на Remnawave

Сначала повторите перенос на копии своей базы и проверьте требования выбранного Remnawave. Сохраните том PostgreSQL, окружение, секреты входа, домены и параметры связи с нодами.

Расширения Remnacust не становятся функциями стандартной панели. Отдельно проверьте лимиты хостов и тегов, персональный безлимит, устройства, управление ядром и доступ пользователей. Сохранение базы не означает равенства возможностей.

## Хранение журнала состояния нод

Стандартный срок хранения — три дня; установленное собственное значение сохраняется. Старые записи удаляются постепенно. Освободившееся место может использоваться PostgreSQL повторно без немедленного уменьшения файлов на диске. Не запускайте блокирующее обслуживание рабочей базы только ради уменьшения отображаемого размера.
