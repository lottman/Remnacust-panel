# Возврат базы к Remnawave

Начиная с исправленной сборки Remnacust 1.1.1 стандартные таблицы снова называются `admin` и `remnawave_settings`. Старые установки использовали `xera_admin` и `xera_remnawave_settings`: обычный Remnawave не находил в них администратора и настройки. Новая миграция возвращает имена существующим таблицам, сохраняя записи, идентификаторы и связи. История уже применённых миграций остаётся на месте.

Обновление также восстанавливает ранее зашифрованные пароли Trojan и Shadowsocks в формат, который читает upstream. VLESS UUID остаётся UUID. Новые и изменённые ключи пользователей записываются в стандартном формате. Доступ к базе и её копиям поэтому должен оставаться закрытым. Это не отменяет шифрование ZIP-копий панели или авторизацию API.

## Обычное обновление Remnacust

Сделайте резервную копию базы и сохраните `.env`. Соберите новый образ из исправленных исходников и обновите панель. При запуске применится миграция имён таблиц, затем seed восстановит старые пароли пользователей. **Сохраните прежний `APP_SECRET`**: новый случайный ключ не расшифрует старые значения. Ошибка расшифровки останавливает запуск и откатывает изменения паролей; она не заменяет их случайными ключами. После исправления ключа запуск можно повторить.

Не изменяйте старые SQL-файлы, `_prisma_migrations` и не запускайте `prisma migrate reset`. Если одновременно существуют старая и новая таблицы одного назначения, автоматическое исправление завершается ошибкой. Сначала проверьте их содержимое по копии: скрипт не выбирает одну таблицу и не удаляет другую.

Пароли восстанавливаются пакетами по 250 пользователей в одной транзакции. Повреждённый пароль в любом пакете откатывает предыдущие пакеты. Если пароль одновременно изменил другой процесс, ремонт сохраняет новое значение. На тесте с 2500 пользователями число запросов сократилось с 2513 до 23, время — с 5,75 до 1,23 секунды; скорость на вашей базе зависит от её размера и подключения.

## Исправление без запуска новой панели

Для прежней установки доступен `scripts/restore-remnawave-database.sh`. Нужен уже собранный новый образ `remnacust-panel:1.1.5`, существующий Compose с сервисами `remnawave` и `remnawave-db` и исходный `APP_SECRET` в окружении сервиса панели. Скрипт не скачивает чужой образ и не создаёт пустую базу.

Сначала проверьте имена таблиц:

```bash
bash scripts/restore-remnawave-database.sh \
  --compose /opt/remnacust/panel/compose.yml
```

Для исправления:

```bash
bash scripts/restore-remnawave-database.sh \
  --compose /opt/remnacust/panel/compose.yml \
  --apply
```

Для отдельно расположенного `.env` добавьте `--env-file /полный/путь/.env`. Если образ имеет другое имя, укажите `--image имя:тег`. Неинтерактивный запуск требует `--yes`.

Если Compose запускали с `-p`, скрипт читает имя проекта из метки существующего контейнера базы. Для установки без фиксированного `container_name` передайте `--project-name имя-проекта`. Если работающая БД в выбранном проекте не найдена, скрипт завершится до остановки служб и изменения данных.

Скрипт останавливает API и фоновые процессы панели, сохраняет PostgreSQL dump, Compose и `.env` в защищённый каталог `/opt/remnacust/backups`, проверяет оглавление dump и выполняет одну транзакцию: переименование таблиц и восстановление паролей. Неверный ключ или конфликт таблиц откатывает всю транзакцию. При ошибке скрипт пытается вернуть только те службы, которые работали до проверки. После успеха процессы панели остаются остановленными: старый backend ожидает прежние имена таблиц, поэтому запускать его снова нельзя.

Раздельные API/processor/scheduler в том же Compose поддерживаются. Скрипт находит основной сервис, службы с тем же образом, `INSTANCE_TYPE=processor` или `scheduler`, а также `remnawave-processor` и `remnawave-scheduler`. Если другие приложения или процессы из отдельного Compose пишут в эту БД, остановите их самостоятельно до восстановления. PostgreSQL и Redis скрипт не останавливает.

Ошибка команды не всегда означает откат: связь с Docker может оборваться уже после фиксации транзакции. Поэтому после ошибки скрипт повторно проверяет имена таблиц и число пользователей со старым зашифрованным форматом. Прежние процессы запускаются только при подтверждённом исходном состоянии. Если БД изменилась или проверка недоступна, они остаются остановленными. Разберите причину по сохранённой копии; не запускайте старый образ наугад.

## Запуск Remnawave

На тестовой базе проверен официальный образ **Remnawave backend 3.4.4**: он принимает историю миграций и читает стандартные записи после исправления. Сначала повторите перенос на копии своей базы. Сохраните PostgreSQL volume, `.env`, секреты JWT, настройки доменов и подключения нод; замените образ и конфигурацию сервиса по инструкции выбранного upstream-релиза. Более старые релизы не проверены. Будущие релизы могут применять дополнительные миграции.

Расширения Remnacust — лимиты хостов/тегов, персональный безлимит, собственные устройства и управление ядром — не становятся функциями обычного Remnawave. Их дополнительные таблицы сохраняются, но upstream их не использует. Отдельно проверьте политики нод, подписки, доступ пользователей и ограничения перед переключением трафика. Сохранение базы не означает равенства возможностей двух панелей.
