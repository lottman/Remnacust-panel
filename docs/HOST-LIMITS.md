# Квота и скорость хостов и тегов

## Проверка задержки при ограничении сайтов

HTTP-пинг обращается к выбранному в приложении сайту **через VPN-хост**. Если разрешён только Telegram, обычный адрес вроде `www.gstatic.com` блокируется и клиент может показать `n/a`, даже когда Telegram работает.

В режиме «Разрешить только» форма хоста показывает URL разрешённого домена с кнопкой копирования. Для Happ с настроенным настоящим Provider ID панель автоматически передаёт `check-url-via-proxy` и HTTP-метод. Адрес должен быть разрешён на всех выданных видимых хостах: настройка действует на подписку целиком. Подходящий пользовательский URL и метод GET/HEAD сохраняются; явно заданные TCP/ICMP не меняются. Если общего домена нет или разрешены только IP/CIDR, остаётся TCP-проверка, которая не подтверждает авторизацию VPN.

В INCY выберите HTTP/INCY-пинг и вставьте URL в настройках подписки вручную. По [официальной документации INCY](https://docs.incy.cc/en/premium-api/#ping-and-sorting), автоматические `defaultPingProtocol` и `pingTestUrl` доступны через Premium API самого клиента; обычные заголовки подписки этого не заменяют. Настройки Happ описаны в [официальной документации](https://www.happ.su/main/ru/dev-docs/app-management#upravlenie-nastroikami-prilozheniya).

Дополнительные сайты и порты не открываются, правила DIRECT не добавляются. URL выбирается из существующих разрешений без сетевых запросов панели. Сайт должен отвечать на выбранный метод; перенаправление на запрещённый домен остаётся заблокированным. Наличие разрешения само по себе не гарантирует, что сайт или VPN-сервер сейчас доступны.

## Настройки лимитов

Настройки находятся в карточке хоста и в настройках его тегов. Лимит пользователя здесь относится к одному пользователю **в выбранном хосте**, а не к одному устройству и не ко всем нодам учётной записи вместе. Отдельное глобальное поле скорости в карточке пользователя не требуется.

| Настройка | Область действия | Единица / API |
| --- | --- | --- |
| Квота пользователя хоста | Расход одного пользователя на данном хосте | GiB в форме; `userTrafficLimitBytes` в байтах |
| Скорость пользователя хоста | Все устройства и соединения одного пользователя на данном хосте, загрузка и отдача вместе | Mbps; `serverSpeedLimitMbps` |
| Скорость устройства хоста | Все соединения одного приватного ключа устройства на хосте, загрузка и отдача вместе | Mbps; `deviceSpeedLimitMbps` |
| Общая скорость хоста | Все пользователи данного хоста вместе | Mbps; `totalSpeedLimitMbps` |
| Квота пользователя тега | Общий расход пользователя на участвующих хостах тега | GiB в форме; `limitBytes` в байтах |
| Скорость пользователя тега | Одинаковый предел отдельно на каждом участвующем хосте | Mbps; `speedLimitMbps` настроек тега |
| Скорость устройства тега | Одинаковый предел каждого ключа отдельно на участвующем хосте | Mbps; `deviceSpeedLimitMbps` настроек тега |
| Общая скорость тега | Общий пул участвующего трафика | Mbps; `totalSpeedLimitMbps` настроек тега |

`speedLimitMbps` **самого хоста** — другое поле: целевой параметр Brutal в клиентской конфигурации. Он не заменяет серверный `serverSpeedLimitMbps`. Для принудительного ограничения нужны совместимые Remnacust Node и Core; лимит не зависит от наличия настройки скорости в клиентском приложении.

## Пример

Для хоста A установите скорость пользователя 2 Mbps. Два устройства пользователя Иван делят эти 2 Mbps; это не по 2 Mbps каждому. У пользователя Анна свой предел 2 Mbps. Общая скорость хоста, если задана, дополнительно ограничивает их суммарный трафик. Это верхние пределы, а не гарантированная полоса сети. С Core 1.1.11 при постоянном равном спросе активные ключи получают примерно равные доли; неактивные ключи не резервируют скорость. Один активный ключ может использовать свободный пользовательский бюджет до собственного предела устройства. При общем пределе хоста/тега очередь сначала делит бюджет между пользователями, затем между их ключами; число соединений не увеличивает долю.

Пример выше предполагает один обслуживающий узел. Если область назначена нескольким нодам, панель консервативно делит её скорость между назначенными нодами; неактивная доля не означает гарантированное перераспределение полосы.

Чтобы назначить правило нескольким хостам, задайте скорость пользователя у тега и включите «Применять скорость пользователя тега» на нужных хостах. На хосте B Иван получит отдельный предел этого хоста. Если нужен общий пул группы для всех участвующих пользователей, используйте именно общую скорость тега.

## Ноль, наследование и единицы

- `0` или пустое значение скорости отключает соответствующий собственный предел; включённые ограничения тегов сохраняются. В списке отсутствие предела отображается как `∞`.
- Квота тега, скорость пользователя, скорость устройства и общая скорость тега включаются у хоста четырьмя независимыми переключателями. Добавление тега не означает снятие собственных лимитов хоста.
- Одновременно действующие ограничения не складываются в большую разрешённую скорость: более строгий предел продолжает ограничивать трафик.
- Скорость задаётся целыми значениями 0–10000 Mbps. Mbps уже означает мегабиты **в секунду**; дополнительное `/сек` не нужно. 8 Mbps приблизительно соответствуют 1 MB/s без накладных расходов.
- Объём квоты задаётся в GiB (1024³ байт). Это не Mbps и не длительность.

В форме сначала расположены квота, соседние поля скорости пользователя и устройства, затем общая скорость и коэффициент учёта. На узком экране поля располагаются в одну колонку. Подпись единицы видна внутри числового поля. Обозначения Mbps и GiB сохраняются на английском при любом языке интерфейса.

## Лимиты автовыбора Xray JSON

Получатель — хост подписки, которому назначен конкретный автовыбор, например «Автоматический». Участники пула задают серверы для подключения. Их квоты и скорость не наследуются подключением через автовыбор.

| Подключение | Где учитывается трафик и применяется скорость |
|---|---|
| Напрямую к участнику | В этом хосте и его включённых лимитах тегов |
| Через автовыбор | Только в получателе и его включённых лимитах тегов |
| Несколько автовыборов одному получателю | Общий предел получателя; число профилей его не увеличивает |
| Разные получатели с одним участником | Независимые пределы получателей |
| Все собственные пределы получателя равны 0, лимиты его тегов выключены | Нет ограничения автовыбора на уровне хоста; общая квота аккаунта сохраняется |

Исчерпанная квота прямого подключения участника не исключает его из автовыбора. Продолжают проверяться доступ пользователя к обоим хостам, статус подписки, HWID и ограничения сайтов. Коэффициент учёта берётся у получателя. Лимит устройства и справедливая очередь сохраняют одну идентичность при переключении между участниками. Пул не предоставляет доступ к чужим серверам и не снимает ограничения общего аккаунта.

Для этого используется миграция `20261104010000_autoselect_quota_ownership`: внутренний маршрут связывает получателя и участника, ключ маршрута выбирает политику получателя на реальной ноде участника. Оба пути статистики, включая журнал ноды, записывают расход в получателя. После удаления участника его маршрут остаётся только для запоздавшего учёта; новые подключения запрещены. Старые выданные прямые ключи не превращаются в ключи автовыбора: обновите подписку в приложении. Уже записанная история расхода не перераспределяется. До обновления подписки старые ключи продолжают учитываться по прежней схеме: раньше прямое подключение и автовыбор использовали один ключ участника.

Node/Core должны поддерживать `remnacust-routed-device-speed-v1` для раздельного учёта маршрутов и общего лимита устройства между участниками. Начиная с панели 1.1.7.95 подтверждённый старый комплект получает обычные ключи и лимиты источников; отдельный учёт получателя отключается с уведомлением о совместимости. Для его включения обновите Node/Core и подписку клиента. Если нативная Remnawave-нода использует inbound, новые ограничения хостов на нём недоступны и для кастомных нод с тем же inbound; отдельные совместимые inbound сохраняют расширения. Сохранённые финансовые резервы не стираются при понижении версии. На современном комплекте политика сохраняет маркер `routedIdentities`: перезапуск и смена ядра не позволяют подменить его несовместимым бинарником. Добавление маршрута само по себе не закрывает прежние прямые ключи на неограниченном входе; ограниченные входы сохраняют защиту. Применение ключей и политики выполняется через синхронизацию ноды; при её недоступности новый ключ может ожидать доставки. Настройка не переносится на группы сторонних форматов без хоста-получателя.

Правила сайтов получателя и участника пересекаются. При сочетании DENY и ALLOW_ONLY пересекающаяся разрешающая запись исключается целиком: например, запрет `ads.example.com` вместе с разрешением `example.com` не оставляет широкий обход запрета. При необходимости задавайте разрешённые поддомены точнее.

## Работа без панели

Скорость обеспечивается локальным ядром. Для ограниченного объёма используются выданные локальные резервы квоты: панель не нужна для каждого пакета, но нужна для выдачи нового резерва. При исчерпании остатка доступ не становится безлимитным. Сброс немедленно получают доступные ноды, остальные — при восстановлении связи; старые резервы на недоступных нодах могут временно увеличить общий расход сверх новой квоты. Подробности учёта и восстановления: [QUOTA-RECOVERY.md](QUOTA-RECOVERY.md).

## Реализация и проверка

Форма сохраняет существующие поля API. Разделение прямого доступа и автовыбора добавляет внутренние маршруты и идентичности миграцией, указанной выше; механизм квот и скорости остаётся общим. Преобразование Mbps в байты в секунду выполняется в политике панели; Core применяет общий bucket владельца в области хоста и отдельный bucket общей скорости.

Существующие тесты Core в `xray/app/dispatcher/host_policy_test.go` проверяют разделение скорости между устройствами и соединениями, независимость пользовательской скорости разных хостов, общую скорость хоста и пул группы:

```bash
cd Remnacust-core/xray
go test ./app/dispatcher -run 'TestHostPolicy(SharesSpeedAcrossConnectionsAndDevices|V2TagUserSpeedIsIndependentPerHost|V2WholeHostSpeedAcrossUsersAndDirections|V2GroupSpeedAcrossHosts)$' -count=1
```

Эти тесты проверяют механизм ядра. Состояние конкретной рабочей ноды проверяется отдельно после доставки политики; сохранённое значение формы само по себе не подтверждает её применение.

## Совместимость и идентичность устройства

Для лимита устройства нужны панель 1.1.7.42, Node 1.1.16 и активный Core 1.1.11 с `remnacust-device-speed-v1` (комплект 1.2.73). Положительный предел на несовместимых нодах отклоняется до сохранения/применения. Выключенное новое ограничение не добавляет неизвестное поле в старую политику. Существующие ключи не пересоздаются. HWID используется для выдачи отдельного аутентифицированного ключа; копии одного ключа считаются одним устройством. Без отдельных ключей невозможно различить физические устройства только по соединениям. Пределы целые, 0–10000 Mbps; в ядре используются небольшие ограниченные пакетные всплески, а не гарантированная побитовая скорость.
