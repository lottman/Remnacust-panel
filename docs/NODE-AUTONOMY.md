# Работа нод без панели

Путь клиент → CDN → прокси ноды → Xray не должен проходить через панель.
Панель выдаёт конфигурацию и права; рабочая нода проверяет ключи локально.
Доступность подписки и добавление новых ключей при выключенной панели — отдельные
операции, они не гарантируются этим механизмом.

## Два состояния установленной ноды

Автономная политика `remnacust-quota-reserves-v1` использует сохранённые сроки
идентичностей и ограниченные локальные резервы USER/HOST/TAG. Прежний 90-секундный
срок политики её не останавливает. Сохраняются скорости, правила назначения,
запреты и сроки подписки. Ключи и состояние ядра восстанавливаются из приватного
checkpoint; квоты сохраняются в журнале. Административная пауза не отменяется
автоматическим восстановлением.

Старая политика без локальных резервов закрывает защищённые подключения после
90 секунд без продления. Простое увеличение этого времени или удаление проверки
позволило бы обходить квоты и сроки. Автоматический координатор переводит
совместимые ноды через проверку возможностей, барьер старого расхода, резервирование
и подтверждение применения. Недоступный участник общей квоты может задерживать
переход; его долг и резерв нельзя просто исключить из расчёта.

## Автономная работа в течение суток

В автономном режиме нет общего таймера «отключить через сутки». Уже выданные
ключи могут работать дольше, если действуют подписка, локальная политика и резервы.
Периодические неудачные обращения к панели сами по себе Xray не останавливают.
Обычная передача трафика и восстановление после падения процесса — разные проверки.

Перед планируемым отключением панели на 24 часа проверьте:

- Последняя политика действительно применена совместимым Node/Core, переход
  квот завершён и нет recovery-паузы. Старый режим с 90-секундной политикой
  не даёт такой автономности.
- Срок пользователя и каждый используемый USER/HOST/TAG-грант заканчиваются
  позже планируемого окна. Остаток пользователя в панели не равен запасу
  конкретной ноды: общий остаток распределён между участниками.
- В каждом локальном резерве достаточно оплачиваемых байтов на загрузку и
  отдачу с учётом коэффициентов. Неиспользованный write-ahead после аварийного
  завершения учитывается консервативно; рестарт не должен пополнять квоту.
- Окно не пересекает сброс календарной квоты. Например, дневная пользовательская
  квота заканчивается на ближайшей границе 00:05 UTC; следующему периоду
  требуется новое финансирование панелью. Локальное продолжение старого
  гранта за этой границей не разрешается.
- Состояние хранится постоянно: `/var/lib/remnacust/run`, `/var/lib/remnanode`
  и `/var/lib/remnawave/core-manager`. Пересоздание контейнера без этих томов
  не эквивалентно обычному перезапуску. Копирование одного состояния на несколько
  нод недопустимо: это копирует ключи и выданный кредит.
- Маршрут клиента/CDN, DNS, прокси и сертификаты ноды не зависят от работающей
  панели. Панель и нода находятся в разных Compose-проектах.
- При `CUSTOM_CORE_URL` старт контейнера отдельно скачивает ядро. Для работы
  при недоступном источнике используйте заранее установленное проверенное
  bundled/managed-ядро; наличие checkpoint не отменяет сетевую загрузку init.

Сутки без панели не означают выдачу нового трафика после исчерпания квоты или
доступ после окончания подписки. Новую заморозку и отзыв, выполненные на панели
во время разрыва, нода получит только после восстановления связи. Для строгого
доступа через календарный сброс нужна отдельная реализация заранее выданных
будущих грантов; она не подменяется увеличением TTL.

### Старая ручная установка без томов

Установщик уже подключает эти каталоги. Если нода запускалась вручную по старому
Compose без `volumes`, не добавляйте пустые тома с немедленным пересозданием:
они скроют старые checkpoint и журнал. Сначала запланируйте перерыв, остановите
контейнер, сохраните согласованные приватные каталоги из его writable layer
через `docker cp -a` и проверьте владельца и права. Только затем подключайте
сохранённые каталоги как тома и пересоздавайте ту же ноду. Сохраните исходную
копию до подтверждения восстановления. Не копируйте рабочий журнал во время
записи, не обнуляйте его и не запускайте второй экземпляр с теми же резервами.

## Локальное восстановление ядра — Node 1.1.23 и Core 1.1.14

Node 1.1.23 проверяет состояние процесса каждые пять секунд. Пока Xray работает,
он не перечитывает checkpoint и бинарник. При подтверждённом падении совместимого
ядра восстановление выполняется из приватного checkpoint под общим барьером
управления, с повторной проверкой процесса и административной паузы. Готовность
подтверждается ответом приватного API того же PID. Занятый барьер или неизвестный
статус не считаются падением и не запускают второй экземпляр.

Предусмотрены не более трёх автоматических восстановлений за час текущего процесса
Node, с задержками между повторами. Последующий crash или ошибка восстановления
останавливает автоматические попытки до успешного явного запуска нового процесса;
обычный hot apply бюджет попыток не сбрасывает. Административный stop и завершение
агента отменяют ожидающее восстановление. Повреждённое состояние квот не обходится.

В Core 1.1.14 исправлен replay сохранённой политики после очистки истёкших грантов:
истёкшая ссылка не блокирует восстановление других действующих грантов, но сама
не создаёт запись журнала и не выдаёт кредит повторно. Для этих исправлений
обновите ноду до Node 1.1.23 и Core 1.1.14; обновление одной панели не заменяет
удалённые компоненты. Проверка использует 24 виртуальных часа, включая перезапуск,
сроки и исчерпание резерва; это не фактический суточный сетевой soak.

## Проверка перед обновлением

Локальная команда внутри контейнера панели:

```sh
node /opt/app/dist/cli.js check-node-continuity
```

Она возвращает JSON и код 0 только при подтверждении готовности. Проверяются все
включённые ноды с назначенным профилем: завершённый автономный режим, общий контроль
квоты пользователя, совпадение сохранённых desired/applied ревизий и источников,
живое подтверждение той же ревизии, экземпляра ядра и журнала квот. Восстановление
БД, активная recovery-пауза, недоступность и изменение состава/политики во время
проверки отклоняют результат. Пустой состав допустим. Результат — снимок состояния,
а не обещание бесконечного резерва трафика или доступности инфраструктуры.

Начиная с панели 1.1.7.76 и установщика 1.2.112, кнопка обновления сразу передаёт
задание службе, без отдельной сетевой проверки нод. Установщик выполняет диагностику
перед остановкой приложений. Неподтверждённая готовность, недоступность проверки или
старый CLI дают предупреждение и не блокируют обновление. Зависимые от панели ноды
могут испытать перерыв связи; предупреждение не означает перевода в автономный режим.

Старый CLI не запускается в интерактивном режиме: сначала проверяется наличие
команды. При её отсутствии используется проверенный новый образ во временном
контейнере с сетью текущей панели, приватным окружением, read-only root и без
дополнительных capabilities или host mounts. Технический вывод остаётся приватным.
Параметр `--allow-disruption` сохранён для совместимости и пропускает диагностику;
для обычного обновления он не нужен. Проверки выпуска, копии БД и Compose остаются
обязательными. Локальные сроки доступа, квоты, восстановление и финансовые барьеры
не отключаются.

`docker compose down`, остановка сервера или ручная остановка ноды обходят эту
проверку. Панель и ноду нужно держать в разных Compose-проектах; CDN должен указывать
на ноду. Обновление самой ноды или её ядра может прервать текущие соединения.

## Границы безопасности

Пакетное применение профиля больше не ставит общую очередь запуска нод на паузу:
конфликты операций ограничиваются отдельно для каждой ноды. Ранее сохранённая
или вручную установленная пауза очереди автоматически не снимается. Если после
старого обновления задания остаются приостановлены, администратор должен проверить
завершение обслуживания и снять паузу в Bull Board. Принудительный запуск очереди
при каждом старте панели мог бы отменить намеренную административную паузу.

- Проверка не выдаёт новый кредит, не снимает блокировки, не изменяет конфигурацию
  и не удаляет старые гранты. Окончание срока или резерва продолжает закрывать доступ.
- При отключённой панели сохраняется последнее подтверждённое состояние. Новую
  блокировку или заморозку, заданную на панели во время разрыва, нода узнает после
  восстановления связи. Немедленный удалённый отзыв без канала связи невозможен.
- Команда использует сохранённые ключи нод: TLS 1.3, проверку своей CA, mTLS и
  короткоживущий RSA JWT. Проверка имени соответствует существующей схеме частной
  CA/SNI нод. Перенаправления запрещены, системный HTTP-прокси не используется,
  SOCKS задаётся только сохранённой настройкой администратора.
- Одновременно проверяются не более восьми нод; ограничены время, размер ответа
  и состав. Ошибки содержат UUID и фиксированный код без адресов, токенов и сертификатов.
- Запуск обновления доступен только администратору в существующем endpoint.
  Нового публичного endpoint или доступа для API-токенов нет.

Подтверждение в SQL само по себе не является живым подтверждением. Координатор
повторно проверяет incarnation перед начальным барьером; readiness не выводится
только из глобальной фазы ACTIVE.
