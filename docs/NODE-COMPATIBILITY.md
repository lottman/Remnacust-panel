# Совместимость с нодами Remnawave

Согласованный комплект Panel **1.1.7.99** — Node **1.1.24**, Core **1.1.15**, Installer **1.2.138**. Предыдущий комплект: Panel 1.1.7.98, Node 1.1.23, Core 1.1.14, Installer 1.2.137. [Изменения](releases/1.1.7.99.md); обновление удалённых нод выполняется отдельно.

Панель Remnacust 1.1.7.99 выбирает формат запросов по версии агента. Для старых нод она отправляет обычный JSON и выполняет операции с пользователями по одному, если массового API ещё нет. Нода не должна обновляться только ради подключения к панели.

Подтверждённая штатная нода получает базовые ключи. Новые лимиты хоста, правила назначения и специальный доступ неактивных пользователей на её inbound недоступны; панель показывает режим совместимости. Если этот inbound разделяется с кастомной нодой, обе используют обычные ключи. Отдельные совместимые inbound сохраняют расширения. Ошибка сети и устаревшая запись версии для другого адреса не отключают ограничения. Старое кастомное ядро без учёта получателя автовыбора использует ключи и лимиты источников; для отдельного учёта обновите Node/Core и подписку. Уже выданные финансовые резервы и блокировки при понижении версии не стираются.

| Remnawave Node | Соединение и API |
| --- | --- |
| 1.0.0–1.4.0 | Старый HTTP API, исходный конфиг Xray; удаление пользователя с тегами inbound. HTTP нужно разрешить явно для конкретного адреса и порта. |
| 1.5.0–2.2.3 | mTLS, исходный конфиг, JSON без сжатия. Массовые операции выполняются через отдельные запросы. |
| 2.3.0–2.3.2 | Zstd, конфиг с служебными параметрами и объединённая статистика. |
| 2.5.0–2.6.1 | Массовое добавление и удаление пользователей. |
| 2.7.0–3.2.2 | Плагины, сведения о системе и загрузке ресурсов. |
| 3.3.0–3.4.1 | Современный API, включая функции проверки геолокации. |
| Remnacust Node 1.1.1–1.1.17 | Современный API с расширениями нашего ядра; собственная нумерация версий. В выпуске 1.2.74 опубликован агент 1.1.17 с Core 1.1.11 и признаком remnacust-device-speed-v1. |

Если старый агент не сообщает CPU, RAM или свою версию, панель показывает отсутствие данных. Неизвестная версия не превращается в нулевую и сама по себе не запрещает запуск профиля.

Геопроверка доступна в Remnacust Node начиная с 1.1.1 и в стандартной Remnawave Node начиная с 3.3.0. Панель учитывает собственную нумерацию Remnacust и метку сборки в версии агента. Недоступность этой отдельной кнопки на старой ноде не запрещает обычную работу профиля и подписок.

## Подключение

Для нод с mTLS сохраните действующий ключ или сертификат и управляющий порт. Не заменяйте их новым случайным значением при переносе панели. Ошибка TLS или авторизации не вызывает переход на HTTP.

В списке IP назначайте роль `MANAGEMENT` управляющим адресам, а `RESERVE` — их резервам. Только эти две роли допустимы для резервных управляющих кандидатов: `OUTBOUND`, `BLOCKED` и остальные роли не разрешают использование адреса для управления. Сам список IP и выбранная вручную роль не подтверждают доступность. Для кандидатов сохраняется один настроенный API-порт ноды; подбор других портов не выполняется.

Проверяйте соединение кнопкой диагностики в карточке ноды: запрос идёт с backend панели с аутентификацией к API ноды. Открытый TCP-порт, DNS-ответ и прежний зелёный статус сами по себе не подтверждают рабочий управляющий маршрут. Учитывайте время проверки и адрес, порт и режим proxy/direct, к которым она относилась. Изменение настроек требует новой проверки; реквизиты прокси не должны попадать в отображение статуса.

Основной адрес и явно заданные резервные IP проходят аутентифицированную API-проверку. Администратор должен указывать только адреса той же ноды: общие TLS/JWT подтверждают доверие панели, но не уникальный UUID ноды. Другую ноду с теми же доверенными ключами или CA такая проверка не отличит. Внешний поиск адресов не выполняется.

`Proxy URL` задаёт SOCKS5 только для управляющих запросов панели к ноде, а не для пользовательского VPN-трафика. Поле скрыто по умолчанию; его можно показать и изменить. Пустое поле означает прямое подключение. Если прокси задан, все резервные IP используют тот же SOCKS5: отказ общего прокси сменой IP ноды не исправляется. Скрытого перехода на direct нет; для изменения маршрута оператор должен явно изменить настройку прокси.

При username/password-аутентификации SOCKS5 по [RFC 1929](https://www.rfc-editor.org/rfc/rfc1929.html#section-3) логин и пароль передаются прокси открытым текстом. Используйте доверенный прокси в приватной сети или через защищённый туннель. Сам канал Node API через mTLS остаётся зашифрованным; это не шифрует отдельный SOCKS5 handshake.

Ноды 1.0.0–1.4.0 обслуживают старый HTTP API. Подключайте такой агент через защищённый туннель или доверенную закрытую сеть. В `.env` панели перечислите только разрешённые адреса и порты:

```dotenv
REMNACUST_LEGACY_HTTP_NODES=10.20.0.2:2222,10.20.0.3:2222
```

Адрес должен быть доступен из контейнера панели и совпадать с адресом ноды в интерфейсе. Соседние порты остаются на HTTPS. `127.0.0.1` внутри контейнера указывает на этот контейнер, поэтому для туннеля на Docker-хосте нужен адрес, доступный из его сети. После изменения `.env` пересоздайте контейнер панели, чтобы применить окружение.

## Какие функции зависят от ядра

Обычные пользователи, подписки, профили и учёт трафика работают через API соответствующей версии агента. Поддержка протокола, транспорта и параметров конфигурации зависит от установленного Xray. Панель не добавляет MASQUE, Hysteria или новый транспорт в старое ядро.

Жёсткие ограничения отдельных хостов и тегов и немедленный отзыв соединений устройства требуют Remnacust Node и нашего Xray. Установка стандартного агента не даёт ему этих возможностей. В подтверждённом нативном режиме настройки расширений сохраняются в панели, но не применяются на соответствующем inbound; базовая конфигурация продолжает работать. Специальные ключи неактивных пользователей без изоляции назначения не выдаются. Обычное подтверждение удаления пользователя не считается подтверждением разрыва уже открытых соединений.

Наличие хоста в подписке определяется его видимостью, разрешениями пользователя, сквадами и действующими лимитами. Потеря связи с управляющим API ноды не исключает разрешённый хост. Панель сохраняет его индивидуальный ключ; общий ключ пользователя вместо него не подставляется. Доставка ключей и политики ноде выполняется отдельно, а новые данные входят в конфигурацию при следующем запуске ноды. Пока сервер недоступен, запись остаётся в клиенте, но подключение может не работать. Проверка отзыва доступа на всех необходимых нодах и блокировки устройств сохраняются.

Если настроена общая квота, совместимая нода использует выданный локальный резерв при недоступной панели. После его исчерпания или при недоказанном состоянии учёта соответствующая область блокируется до безопасной сверки. Отсутствие связи не превращает лимит в безлимит. Сброс доступные ноды получают сразу; недоступные могут продолжать расходовать старый резерв до подключения. [Скорость и квоты](HOST-LIMITS.md).

## Режим совместимости и ошибки применения

В режиме совместимости карточка сообщает, какие расширения недоступны. Подтверждение относится к конкретным адресу, порту и proxyUrl. Отсутствие ответа от управляющего API не является подтверждением нативного режима. Для старого нашего Core отдельно показывается использование лимитов участников вместо учёта получателя автовыбора.

На совместимой кастомной ноде ошибка обязательной политики сохраняет рабочую конфигурацию и не отправляет неподтверждённую замену. Это относится также к уже активированным финансовым резервам: понижение версии не должно освобождать их повторно. Если Xray остановлен или нода недоступна, она не объявляется исправной.

Временный сбой синхронизации на совместимой ноде показывается отдельным предупреждением. Панель повторяет применение ожидающей конфигурации не чаще раза в минуту. После успешного обновления агента, применения политики и запуска конфигурации предупреждение исчезает. Нельзя обойти проверку поддержки расширения, подавив ошибку или подставив общий ключ пользователя.

## Проверки

Тесты используют исходные схемы API всех 47 опубликованных тегов Remnawave Node от 1.0.0 до 3.4.1. Проверяются запуск, здоровье, статистика, добавление и удаление пользователей, формат сжатия и обработка ошибок. Исходные схемы, ссылки на коммиты и лицензия сохранены в `panel/backend/tests/fixtures/remnawave-node-contracts.json`.

```bash
cd panel/backend
node --test tests/node-version.test.cjs tests/node-compatibility.test.cjs tests/host-preparation.test.cjs
```

Это проверка совместимости запросов и ответов. Все 47 старых контейнеров и все клиентские протоколы в реальном трафике не запускались. После переноса конкретной ноды проверьте подключение клиента и изменение расхода.

Исходные материалы: [официальные теги Remnawave Node](https://github.com/remnawave/node/tags), [установка ноды](https://docs.rw/docs/install/install-node).

Для немедленного отзыва уже открытых соединений используйте ноду 1.1.5 с ядром 1.1.5. В прежнем ядре оптимизированная передача могла обходить закрытие внутренних буферов. Исправленное ядро закрывает соединение авторизованного устройства; другие устройства за тем же IP остаются подключёнными. Массовое обновление удалённых нод автоматически не выполняется.

## Самостоятельное восстановление состояния

Remnacust Node 1.1.9 с панелью 1.1.7.31 запрашивает актуальную конфигурацию после запуска и восстановления связи. [Очередь удаления устройств, миграция и ограничения](DEVICE-RECONCILIATION.md). Первое подключение по-прежнему назначается панелью; старые агенты используют прежние проверки связи со стороны панели.
