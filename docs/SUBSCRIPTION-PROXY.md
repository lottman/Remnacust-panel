# Прокси подписок на отдельном сервере

Русский · [English](SUBSCRIPTION-PROXY.en.md)

## Что именно проксируется

Клиент → отдельный прокси sub.example.net → сервер страницы подписки 198.51.100.20 → API панели. Это прокси выдачи подписки, а не VPN-трафика ноды. Вместо DNS-разрешения источника прокси соединяется с заданным IP; Host выбирает сайт источника, SNI и проверка сертификата подтверждают его имя. В примере origin.example.net — основной домен страницы, sub.example.net — его CDN/прокси-домен. Все адреса и ключи здесь учебные. Адрес панели нужен только странице на сервере, клиенту его не передавайте.

## Подготовка в панели и на серверах

В «Подписка → Настройки → Страницы подписки» добавьте основной origin.example.net и дочерний CDN sub.example.net. В «Настроить CDN» скопируйте индивидуальные имя и значение заголовка запросов. Имя имеет вид X-…; значение содержит UUID и подпись. У каждого CDN своя пара. DNS sub.example.net направьте на отдельный прокси, сертификат источника должен подходить origin.example.net. На источнике HTTPS-сайт должен передавать весь путь в актуальную страницу подписки. Её REMNAWAVE_PANEL_URL и API-токен остаются в приватном серверном .env. Если страница находится на другом сервере, обновляйте её отдельно от панели.

## CDN перед отдельным сервером и старые ссылки

Вариант с провайдером CDN: клиент → CDN → origin.example.net на отдельном сервере → Caddy → локальная страница подписки → приватный API панели; ответ возвращается тем же путём. Публичный sub.example.net направьте на CDN записью A или CNAME по инструкции провайдера. Источник CDN — HTTPS-адрес страницы либо её IP; Host и SNI — origin.example.net. Индивидуальную пару заголовка из панели настройте в ЗАПРОСАХ CDN, а не в ответах. На источнике Caddy передаёт полный запрос локальной странице; порт 3010 здесь пример, используйте свой опубликованный порт и привяжите его только к loopback. Пример ниже относится к Caddy на том же хосте; в Docker с отдельной сетью используйте имя сервиса и его порт вместо 127.0.0.1.

```caddyfile
origin.example.net {
    reverse_proxy 127.0.0.1:3010
}
```

Для переезда без отключения клиентов оставьте legacy.example.net зарегистрированным основным доменом с открытым доступом и рабочим HTTPS-прокси к странице. Не удаляйте его DNS и сертификат: существующие импортированные ссылки продолжают работать. Назначьте origin.example.net доменом по умолчанию и выдавайте новым клиентам CDN-ссылку sub.example.net из карточки пользователя или API ссылок. Старые явные привязки пользователей меняются отдельно; их ключи менять не нужно. В SUB_PUBLIC_DOMAIN остаётся основной домен источника, синхронизированный с настройкой панели: не подменяйте его дочерним CDN. Если новый основной домен не должен выдаваться клиентам, используйте для него «Только через CDN» или «Перенаправлять на CDN». Старый адрес в уже импортированной подписке сам не исчезнет. Одного блока Caddy без регистрации старого домена в панели недостаточно: незарегистрированное имя может быть отклонено. Снимайте старый домен только после перехода клиентов.

## Передавайте весь путь, а не только страницу

Проксируйте /KEY, /KEY/json, ссылки устройств и весь /geofiles/... вместе с .dat, .sha256 и параметрами запроса. Если задан префикс подписки, сохраняйте его. Примеры ниже предполагают пустой префикс. Не добавляйте /api/sub к каждому запросу: это другая схема, прямое обращение к API панели. Не обрезайте URI и не перенаправляйте на служебный адрес. Передавайте исходные User-Agent, Accept, HWID-заголовки клиента и заголовки ответа Routing, Profile-Title, Subscription-Userinfo, Content-Type, ETag. Перезаписывайте только собственный CDN-заголовок. Не принуждайте кэширование страниц, подписок и ошибок; для DAT соблюдайте Cache-Control источника. HTML с HTTP 200 ещё не подтверждает выдачу JSON и геофайлов.

## Caddy: HTTPS к IP источника

На отдельном сервере укажите этот блок в Caddyfile. В окружении сервиса Caddy задайте SUB_ORIGIN_HEADER и SUB_ORIGIN_VALUE из «Настроить CDN»; храните их приватно и не публикуйте развёрнутый конфиг. Caddy получает сертификат публичного домена при доступности ACME; этот пример не настраивает DNS и firewall. Host задан явно также для Caddy 2.9/2.10. TLS-сертификат источника проверяется штатно; tls_insecure_skip_verify не нужен.

```caddyfile
sub.example.net {
    reverse_proxy https://198.51.100.20 {
        header_up Host origin.example.net
        header_up {$SUB_ORIGIN_HEADER} {$SUB_ORIGIN_VALUE}
        transport http {
            tls_server_name origin.example.net
            dial_timeout 5s
            response_header_timeout 30s
        }
    }
}
```

## Nginx: HTTPS с проверкой имени

Нужен действующий сертификат публичного домена. В приватном /etc/nginx/private/sub-origin-header.conf сохраните ровно одну директиву proxy_set_header с индивидуальными именем и значением из панели. Учебную пару ниже обязательно замените. Файл вне webroot, доступ только администратору; стандартный root-master Nginx читает его при запуске. При непривилегированном запуске обеспечьте чтение только нужному сервису. proxy_pass без URI сохраняет исходный путь и query; проверка сертификата и SNI включены явно.

```nginx
server {
    listen 443 ssl;
    server_name sub.example.net;
    access_log off;
    ssl_certificate /etc/letsencrypt/live/sub.example.net/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/sub.example.net/privkey.pem;
    location / {
        proxy_pass https://198.51.100.20;
        proxy_http_version 1.1;
        proxy_set_header Host origin.example.net;
        proxy_set_header Connection "";
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
        include /etc/nginx/private/sub-origin-header.conf;
        proxy_ssl_server_name on;
        proxy_ssl_name origin.example.net;
        proxy_ssl_verify on;
        proxy_ssl_trusted_certificate /etc/ssl/certs/ca-certificates.crt;
        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
        proxy_cache off;
        proxy_buffering off;
    }
}
```

## Проверка и ошибки

Список запросов Nginx в примере отключён, чтобы ключ подписки не попадал в обычный access log. Ограничьте доступ к журналам ошибок: они тоже могут содержать URI. Для проверки введите тестовый KEY скрыто и нажмите Enter; JSON сохранится в отдельном приватном каталоге. Удалите его после проверки.

До ограничения origin проверьте конфиг через caddy validate --config /etc/caddy/Caddyfile либо nginx -t. В командах ниже KEY — приватный ключ своей тестовой подписки: не отправляйте его в публичные логи. Первая команда с --resolve проверяет IP, SNI и сертификат, обходя DNS источника, но не правила доступа. После включения «Только через CDN» прямой запрос без подписанного заголовка должен получить 403. Вторая команда проверяет прокси. Для каждого поддерживаемого приложения проверьте также базовую ссылку с его реальным User-Agent. Из Routing-заголовка получите фактические ссылки DAT и скачайте их с контрольными суммами: произвольный /geofiles/test.dat не является проверкой. 404 только на геофайлах — проверьте маршрут /geofiles и версию страницы на источнике; 403 — режим/имя/значение CDN-заголовка; 502/504 — соединение прокси с источником, TLS и журналы origin. Не увеличивайте таймаут до бесконечности.

```bash
umask 077
CHECK_DIR=$(mktemp -d)
IFS= read -r -s KEY
curl --fail --silent --show-error --resolve origin.example.net:443:198.51.100.20 "https://origin.example.net/${KEY}/json" -H 'User-Agent: INCY/2.6.2/ios' -o "$CHECK_DIR/origin.json"
curl --fail --silent --show-error https://sub.example.net/KEY/json -H 'User-Agent: INCY/2.6.2/ios' -o "$CHECK_DIR/proxy.json"
```

## Ограничение источника и приватность

После успешных проверок включите «Только через CDN» у основного домена: правильная подписанная пара разрешает origin-запрос. «Перенаправлять на CDN» открывает клиенту 307, а «Закрыт» запрещает всю семью вместе с CDN — это разные режимы. Последний основной домен нельзя полностью закрыть. Для сетевой изоляции отдельно разрешите HTTPS источника только IP прокси/CDN, сохраняя SSH, API управления и выпуск/продление сертификатов; учтите внешний firewall хостинга. По приватной защищённой сети можно вместо HTTPS origin передавать HTTP напрямую порту страницы с Host публичного домена; не открывайте этот порт всем и не передавайте ключи по публичному HTTP. CDN-заголовок не является API-токеном и не скрывает IP источника из DNS/истории. Служебные адреса, Authorization и секрет CDN не должны попадать в тело, Location, заголовки ответов или webroot.
