# Автовыбор и история шаблонов

Шаблоны Xray JSON редактируются кодом и во вкладке **Автовыбор**; обе вкладки используют один черновик. Клиентские форматы sing-box, Mihomo, Clash и Stash используют собственные поддерживаемые группы.

Состав пула обновляется вместе с подпиской. Сервер для нового соединения выбирает приложение. Панель не выбирает сервер для каждого пакета и не измеряет загрузку CPU клиентского маршрута.

## Источники и получатели

Источники — хосты, через которые может пройти соединение. Получатели — хосты, в подписке которых используется автовыбор. Эти настройки независимы; назначение не предоставляет пользователю новых прав.

Выберите конкретные хосты, точные теги, условие по имени/тегу или теги получателя. Видимость, права пользователя, состояние хоста, ограничения и исключения формата применяются к итоговому набору.

| Режим пула | Когда выбираются участники |
| --- | --- |
| Все выбранные | В подписку входят все подходящие участники; дальше выбирает клиент |
| Случайные | При обновлении подписки выбирается указанное число участников |
| Группа | При обновлении подписки выбирается одна непустая подходящая группа |

Для случайной выборки задайте количество от 1 до 1000. Если подходящих хостов меньше, используются доступные. Это не случайная смена состава при каждом соединении.

Для точного порядка выберите конкретные хосты и все выбранные участники, затем используйте **Порядок серверов**. Фильтр IPv4/IPv6 оставляет только явные IP выбранного семейства; доменные имена используйте в режиме **Любой адрес**. Этот фильтр не определяет DNS-результат имени.

## Стратегии подключения

| Выбор | Поведение и ограничения |
| --- | --- |
| Минимальное время ответа (ping + TTFB) | HTTP-проверка через каждый сервер; это не отдельный ICMP ping |
| Распределять соединения | Новые соединения циклически распределяются между доступными участниками |
| Приоритет: первый доступный | Используется первый работающий сервер в выбранном порядке |
| Случайное подключение | Клиент выбирает случайного участника; состав пула при этом не меняется |
| По очереди | Обычный round-robin; настройка проверок и резервного выхода имеет самостоятельное значение |
| Ручной выбор | Пользователь выбирает сервер в приложении |

**Распределять соединения** не означает измерять CPU, память, число пользователей или свободную полосу. Открытые соединения остаются на прежнем сервере; одинаковое число новых соединений не гарантирует равный объём трафика.

| Формат | Режим распределения |
| --- | --- |
| Xray JSON | roundRobin с HTTP-проверками; после подтверждённого отказа всех участников трафик блокируется, если свой резервный выход не задан |
| Mihomo, Clash, Stash | Нативная группа load-balance со стратегией round-robin |
| sing-box | Явно используется urltest: выбор по времени HTTP-ответа; циклического распределения соединений нет |

До первых результатов HTTP-проб доступность неизвестна, и участник ещё может быть выбран. Явно заданный резервный выход сохраняется. Проверьте его назначение: прямой выход означает именно прямое соединение, если вы выбрали его самостоятельно.

Для заданного порядка round-robin поддерживается до 128 участников одного балансера и до 256 на конфигурацию. Приоритетный режим не переносит уже открытые соединения. Проверьте поддержку стратегии в используемом приложении.

## HTTP-проверки

Проверку выполняет приложение через участника пула. Время включает установку соединения, TLS для HTTPS и ожидание HTTP-ответа. URL должен возвращать небольшой ответ, желательно 204, и быть доступным через весь пул.

Пользовательские URL, интервалы и явно заданный метод сохраняются. Для отсутствующих настроек используются URL https://www.gstatic.com/generate_204 и интервал 30 секунд. Для burstObservatory по умолчанию применяется HEAD, тайм-аут 5 секунд и два измерения. Явный GET может учитывать чтение тела ответа.

leastPing, leastLoad и режим распределения с проверками требуют наблюдений. Обычные random и roundRobin без резервного выхода не требуют дополнительных проверок. При явно заданном резервном выходе доступность участников также должна проверяться.

Заблокированный сайт проверки может исключить исправный для других целей сервер. При ограничении сайтов используйте разрешённый адрес проверки для всех участников. TCP-проверка не подтверждает авторизацию VPN.

В leastLoad доступны expected, tolerance, baselines и maxRTT. Это параметры отбора по результатам наблюдений, а не телеметрия CPU ноды. tolerance — доля неудачных проверок: 0.01 означает 1%, 1 — 100%, 0 отключает эту проверку. Остальные ручные параметры сохраняются при изменении одного поля.

## Назначение и лимиты

В разделе **Где использовать автовыбор** выберите конкретную группу и хосты либо теги получателей. Прямое назначение хосту имеет приоритет над тегом. Явно выбранный в карточке хоста шаблон также сохраняет приоритет. Назначение не отменяет DIRECT, REJECT и доменные правила.

Квоты и скорость автовыбора задаются у получателя. Несколько групп одного получателя делят его ограничения. Учёт получателя требует совместимых Node/Core; после обновления компонентов обновите подписку. [Области лимитов](HOST-LIMITS.md).

## Сохранение и история

После смены стратегии сохраните шаблон и обновите подписку в приложении. Дальнейшие HTTP-измерения клиент выполняет по своему расписанию без повторной загрузки подписки.

Некорректный JSON/YAML или неполная настройка могут сохраняться как черновик с предупреждением. Рабочая подписка продолжает использовать активную версию до успешного применения исправленного кода.

Для Xray JSON, sing-box, Mihomo, Clash и Stash хранятся последние 30 версий. История показывает дату и сравнение с текущим черновиком. **Открыть в редакторе** восстанавливает весь код; несохранённый текст заменяется после предупреждения. Сохранение создаёт новую версию, поэтому восстановление тоже можно отменить.

Редактор текста открывается независимо от списка хостов. При ошибке списка повторите его загрузку перед выбором участников; ошибка не должна восприниматься как пустой пул.
